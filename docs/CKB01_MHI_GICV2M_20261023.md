# CKB01: IPA MSI reception and GICv2m experiment (2026-10-23)

## Confirmed result

The same kernel and USB rootfs that lose IPA-generated completion interrupts with the DWC internal MSI controller successfully handle them when PCIe0 uses the existing SoC GICv2m controller. Only the FIT DTB was changed. No software event consumption, endpoint reset, firmware download or SDX55 persistent change was used for the successful run.

This establishes a host MSI receive-path interoperability problem with the OEM IPA path. It does **not** establish the exact on-wire TLP length, byte enables or attributes responsible for DWC not capturing the write. It is not evidence of an incompatible MHI packet protocol.

## Evidence and boundary tracing

Raw files are in `../research/mhi-msi-rootcause-20261023/` in the local project.

1. `map-window-evidence.tar.gz`: SDX55 outbound iATU region3 maps local PCIe addresses `0x10000000000..0x100ffffffff` to PCIe addresses `0..0xffffffff`. Therefore IPA destination `0x10044d79000` becomes PCIe target `0x44d79000`. The high bit is part of the endpoint routing aperture. Region1 separately maps the CPU MSI alias at `0x10040002000` to that same host MSI target.
2. `ipc-window-evidence.tar.gz`: reads through the verified CPU MSI alias return the IPA payloads `0x15`/`0x16`, while DWC status and the corresponding handler counts stay zero. The writes reach host memory instead of being captured as DWC MSI.
3. `generator-window-evidence.tar.gz`: CPU write to the verified MSI alias and PARF_MSI_GEN both trigger the previously missing IRQs. DWC vectors18,21,22 change from zero to 1,2,1 respectively. This excludes a blanket masking, vector allocation or host-handler failure.
4. `attributes-ab.txt`, `nosnoop-ab.txt`: clearing PCIe DevCtl NoSnoop/Relaxed Ordering permissions does not restore IPA interrupts. This does not measure actual AXI-generated TLP attributes. Original DevCtl restored.
5. `high-address-capture-test.txt`: temporarily testing DWC address-high `0x100` does not capture IPA MSI. Original value restored.
6. `gic-first-ssh.txt`, `gic-control-proof.txt`: GICv2m route produces ordinary completion interrupts and working control transactions with diagnostic software consumption disabled.

### Successful GICv2m run

- Host boot ID: `da47e369-de0e-49c7-b0a4-280a97cb5761`.
- MSI address: `0x0b00a040`.
- Linux-allocated endpoint MSI data base: `0x1d0` (SPI464); do not hardcode the OEM base448 into the MHI table. The root port also allocates from this frame.
- IRQ domain: `GICv2m-PCI-MSI` -> `GICv2m` -> GIC.
- At roughly98 seconds, MSI offsets2/5/6 already have counts50/658/656; previously these remained zero under DWC.
- `enabled=0 polling=0 dead=0 consumed=0 rounds=0` before and after the control probes.
- Management ping: 5/5, 0% loss, average1.873ms.
- OEM root command: SDX55 `uname -a` and uptime returned.
- QMI14 and QRTR DMS revision/UIM queries: successful.
- OEM baseband remains `MPSS.HI.2.0.3-00217-SDX55_CPEALL_PACK-1.576560.2.578897.2`.
- Existing automatic bootstrap also obtained WDA raw-IP / no aggregation from measured PCIe endpoint4. Existing cellular autostart then attempted data setup and backed off; this is not proof of a working cellular data session. `ifdown cellular` was issued to isolate the MSI experiment and IP_HW0 was confirmed DOWN.

## Minimal board correction

CKB01 alone adds a label / zero-cell MSI specifier to the existing GICv2m frame under `&intc`, and sets PCIe0 `msi-parent` to it. Other boards, PCIe1, event layout, channel configuration and power policy remain outside this change.

The pinned DWC host source selects its internal controller only when there is no `msi-parent`, `msi-map` or custom MSI initializer. The existing kernel already initializes GICv2m (`SPI[448:479]`), supports multi-vector PCI MSI and composes the address/data; no new interrupt controller implementation is required.

FIT checker and generated fixtures are updated together. Missing GICv2m routing is an advisory CI verification failure under the existing workflow; raw ITB/IMG/log upload behavior is preserved.

## Limitations and recovery

A previous read of an unverified generic endpoint CPU address stalled module control. Do not repeat it. A true cold boot restored QRTR. This read is not part of the correction. Only verified register windows and aliases should be used in further experiments.

The DWC repeat subsequently recovered SSH (boot `4c238fbc-331c-43a1-9367-decfd2397da4`). Its measured results reproduce the fault: ping5/5 lost, OEM proxy timeout, QMI14 CID allocation timeout, QRTR success, ER1/4/5 interrupt counts0 with `consumed=0`. See `dwc-repeat-proof.txt`. The GICv2m repeat also passed (boot `e92b57b8-31ea-4020-b973-69226b0c5170`): ping5/5, OEM root command, QMI14 and QRTR queries successful, ER1/4/5 IRQ counts34/285/260 by58s, with `polling=0 consumed=0`. See `gic-repeat-proof.txt`. Thus the result was reproduced in both switching directions. The USB default FIT now contains the working GICv2m variant. The early Wi-Fi reconnect timeout is tracked separately from these measured MSI results.

Long-run stability, repeated cold boot, DIAG packet exchange, cellular data and n78 require separate acceptance evidence. The two software-requested GICv2m starts passed control probes; do not count the whole sequence as three cold/three warm boot acceptance. A complete new kernel build has not been performed for this DT-only experiment.
